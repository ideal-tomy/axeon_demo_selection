`src/data.js` を実行して確認した現在のデータは31件、`listedDemos()` は10件で、掲載10件はすべて `linkState: available`。本計画でいう「全ページ」は、厳選版に掲載されている10件（基準1件＋反映9件）を指す。非掲載21件の公開・追加制作は対象に含めず、共通処理変更による表示への影響を回帰確認する。

## 2. 旧計画との差分と根拠

既存の `construction-record-detail-page-rollout-plan.md` は原稿の参考資料として残す。構成と実装手順は本計画を優先する。旧計画にある「こんな業務に」「詳しい操作方法」「関連デモ」を一律追加すると、完成した建設ページと異なる構成になるため採用しない。

今回確認したのはローカルのソース、画像ファイルの存在、掲載データ、既存検証スクリプト。ブラウザでの最新表示と外部デモの機能確認は未実施であり、工程0・1で実施する。過去資料の機能説明は確認済みの事実として扱わない。

| 実装 | 確認した内容 |
|---|---|
| `src/demo-story.js` | 建設は `constructionModel()`、他9件は `thinStoryModel()`。単純にthinを解除するだけでは必要なモデル項目が不足する |
| 同ファイルの建設モデル | `toolIntroLayout`、`compareConstruction`、`conditionAccordion`、`closingStrong` が有効。`details` は未設定、`related` は空 |
| 同ファイルの描画処理 | プレビュー見出しに建設固有の「写真整理から提出後の確認まで」が直接記述されている |
| `src/style.css` | `story-layout-tool-intro` に完成版の表示規則がある。PCでは3列、スマートフォンでは横スクロール。Hero画像は700px以下で非表示 |
| `src/main.js` | ギャラリーのドット同期、詳細表示、戻る操作、フォーカス管理を共通処理している |
| `scripts/verify-construction-redesign.mjs` | 操作手順・対象業務・関連デモがないこと、利用条件の開閉、PC／スマホの比較表示を検証する既存コードがある |
| `scripts/verify-detail-rollout.mjs` | 対象21件・除外7件など旧件数の固定値と旧構成の期待値があり、現状のまま合否判定に使えない |

## 4. 共通化の設計

### データと描画の分離

各 `src/*-story.js` にページ固有の原稿を置き、`src/demo-story.js` に共通モデル生成処理を設ける。ページごとに建設用HTMLをコピーしない。

追加する原稿項目の案：

```js
{
  heroImage: '/images/demos/<id>/top.png',
  previewTitle: '各デモの3場面をまとめた見出し',
  steps: [/* 3件。短いheadline、subtitle、画像に対応したalt */],
  changes: [/* 現状と変更後の組を3件 */],
  conditionSummary: [/* 常時表示する短い説明 */],
  conditionTitle: '利用条件・データを使う際の注意',
  conditions: [/* 確認済みの利用条件 */],
  closingTitle: '実際に試してみる',
  closing: 'デモ固有の短い案内'
}
```

既存の `title`、`intro`、`meta`、`cta` は利用する。上記は実装時の設計案であり、画像パスは新規用意した場合のみ設定する。

### 具体的な変更

1. 共通モデルに完成版の表示フラグを集約し、プレビューへ `compact: true`、`stepBadge: true` を設定する。
2. プレビュー見出しを `m.previewTitle` から表示し、必ずエスケープする。建設の現行見出しも同じフィールドで表現する。
3. `constructionToolCompare()` の構造を共有する。初回は関数・CSSクラスの大規模な改名を避ける。写真用など業務に合わないアイコンはモデルで指定可能にするか、汎用アイコンへ置き換える。
4. 利用条件は文字列配列から既存の `list()` と `esc` で描画する。新しい生HTML原稿を増やさない。
5. 建設も同じモデル生成処理に載せ、共通化前後で文面・画像・表示が変わらないことを確認する。建設固有の原稿移動は表示を変えない範囲に限る。
6. 他9件を順次共通モデルへ切り替える。9件の移行後に不要となったthin専用モデル・ラッパーを参照確認のうえ整理する。非掲載デモが使う `demoModel()` は維持する。
7. `main.js` のギャラリー初期化が全対象で動くことを確認する。構造を維持できるなら処理変更は不要。

## 5. 画像と原稿の準備

画像は `data.js` の `shots[].image` を既存プレビューの正本とし、`story-images.js` はフォールバックとして扱う。まず3場面との対応を点検し、不一致・古い画面・文字が読めない画像のみ撮り直す。

Heroは建設の `top.png` と同じ役割を持つ、各デモの実画面による横長の代表画像を用意する。既存の `entry.jpg` や `catalog.jpg` は内容・解像度・トリミングを確認して採用する。縦長画像の引き伸ばしや、未実装UIの画像作成は行わない。作業中は既存 `heroStage()` のプレビュー画像表示を利用できるが、完了時には各ページの代表画像を確定する。

| デモ | 3場面の原稿の起点（要実画面照合） | 特に確認すること |
|---|---|---|
| internal-knowledge | 質問／回答・手続き／根拠規程 | 設定での自社文書追加・接続切替の範囲 |
| approval-inspection | 照合／保留理由／承認記録・基準 | 4画面を3カードで紹介する対応、画像内ボタンは操作不能という説明 |
| quality-incident | 発見／原因候補／是正・承認 | 原因の自動確定と誤認させない、提出・PDFの実際の挙動 |
| logistics-dispatch | 今日の手配／帰り荷候補／未確認事項 | 自動配車・運賃確定・実送信の有無 |
| kaigo-handoff | 申し送り／面談記録／日報 | 録音と固定サンプルの区別、再読み込み・タブ終了時の保存挙動 |
| field-dandori | 依頼／段取り／申請・人員準備 | 画面上の操作名、実申請・配置依頼との違い |
| gym-facility | 利用状況／設備記録／画像確認 | 対応要否の入力結果、履歴への反映・保持範囲 |
| dd-ma | 企業選択／改善策・試算／第3場面の確認 | 「問いと返した時間」等の既存未確定表現、ライブ機能とサンプルの区別 |
| wholesale-quote | 問い合わせ／在庫表／返信下書き | 下書きの編集可否、見積の範囲、返信・在庫引当の有無 |

比較文は「時間を○％削減」など未計測の効果を足さず、作業の違いを示す。利用条件はデモごとに確認し、建設の「保存しない」「APIキー不要」を一括転記しない。特に `sessionStorage` の利用だけでは再読み込み時の消去は断定できないため、実装・挙動の両方を確認する。

未確定事項は、ページID・論点・確認した画面／実装・対応方針を記録する。確認できない機能は新しい説明へ盛り込まず、確認済みの範囲で原稿を成立させる。
